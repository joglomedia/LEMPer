# LEMPer security audit remediation

This register tracks all 41 source-review leads from the LEMPer audit. Each row describes the repository change and what it means for an existing installation. The original audit did not establish exploitation or compromise. Applying a source update alone does not rotate credentials, reload services, replace customized configurations, or remove privileges already issued on a server.

## Existing installation priorities

1. **Accounts and grants.** If hosting users were created with the bootstrap password, rotate the bootstrap account and affected hosting accounts independently, including their HTTP credentials. Rebuild a previously web-writable `/srv/.htpasswd` using trusted account records and set it to `root:www-data` mode `0640`. Review existing MariaDB schema grants containing underscores. Grant the intended literal schema, verify the account's access, then revoke only the obsolete pattern after checking who relies on it. Review earlier backups and rotate secrets if unauthorized access was possible.
2. **Web administration and virtual hosts.** If the administration document tree was web-owned, take the panels offline, save the old tree as an opaque backup in a root-only location outside every served directory, and install fresh code in a new root-owned tree from a trusted release. A recursive ownership change cannot establish the provenance of old executable files. Reinstall any previously derived privileged helper, including `/etc/lemper/cli-plugins/lemper-tfm`, from fresh trusted source before using it. Recreate panel settings from the protected profile. Restore reviewed static data and ACME challenge routing separately. Preserve customized Redis and Memcached client configuration and test each connection after changing endpoints. Apply the virtual-host and jail migration instructions before reopening access. Enroll verified administrators in the dedicated `/etc/nginx/lemper-admin.htpasswd` file. [Virtual-host migration](FEATURES.md#updating-existing-managed-virtual-hosts)
3. **Service endpoints.** Coordinate changes to existing cache clients, FTP clients, mail submission, and database accounts before changing service configuration. The shared Redis password grants access to the entire instance. Use separate instances or appropriately scoped ACLs for independent tenants. phpMemcachedAdmin uses the private `www-data` instance. [Data service authentication](DATA_SERVICE_AUTH.md) · [Memcached endpoints](FEATURES.md) · [Mail](MAIL.md)
4. **Backups and updates.** Keep an independently trusted recovery copy before changing a host. Explicitly set `LEMPER_LEGACY_DIR` for a nonstandard legacy checkout whose dotenv belongs in a configuration backup. Review scheduled Restic sources and reselect a suitable scope where a parent directory belongs to a tenant. [Config backups](MAINTENANCE.md) · [Restic sources](DATA_BACKUP.md)
5. **Host policy.** Verify effective SSH settings for actual administration accounts and client networks. Keep recovery access available during SSH, firewall, and PHP-FPM activation. Resolve conflicting firewall ownership through a scheduled migration. Test deployed daemons, including real clients and customized policy, before closing an operational finding.

## Verification and remaining deployment checks

The final Ubuntu 26.04 checkout passed all **604 tests** in `bash scripts/run_tests.sh`, with zero skips. Bash syntax, ShellCheck with sourced-file analysis, CI Bashate, and `git diff --check` passed. The 41 fingerprints above match the original report exactly.

| Component | Observed in disposable Linux environments |
|---|---|
| Nginx and Fail2ban | Nginx 1.28.3 served real HTTP and TLS fixture requests. A hosting credential worked on its own vhost and received HTTP 401 on the Redis and Memcached administration paths. An administrator could access the management listener. The fixture also exercised WordPress Multisite media, same-owner symlinks and cache hits, bypasses and private responses. Jail reload and rollback used a Fail2ban stub. |
| Mail | Debian 12 passed 18 mail unit tests and 18 offline mail integration checks. Authenticated submission accepted an assigned alias with a different owned envelope, produced the expected DKIM signature, rejected an unassigned or duplicate From, and deferred when the author filter stopped. The same run checked configuration backup and verification. Rspamd configuration also passed on Ubuntu 22.04 and 26.04. |
| SQL, caches and MongoDB | MariaDB 11.8 stored one literal escape per schema underscore and accepted a connection to the intended schema. Real Redis and Valkey daemons required authentication. Memcached enforced Unix socket ownership and authenticated SASL access. MongoDB 7.0 enrolled and retried the test administrator and denied anonymous administrative access. A separate systemd check showed MongoDB failed before startup when bootstrap network isolation was unavailable. |
| FTP, host policy and recovery | The Ubuntu package wrapper and bundled Pure-FTPd wrapper both emitted PAM authentication and TLS mode 3. SSH checks used real OpenSSH effective-policy evaluation. PHP-FPM activation, firewall transitions and system configuration restore used isolated files or service doubles, including failure and rollback cases. |

The verification covered repository behavior and disposable fixtures. Full host installation and upgrade, production restore, live firewall changes, distro-wide package compatibility, and successful systemd namespace setup for MongoDB remain deployment checks. The offline mail run excluded external relay, online package updates and package removal. The original report and these checks establish no history of compromise on any particular host.
